一张图看见全局，一套语言精准落地。
用户故事地图 · BDD · Gherkin · Feature 文件

01 用户故事地图

🧩
痛点：需求列表像一根长长的绳子
敏捷团队通常把需求写成“用户故事”，塞进一个清单里。
时间一长，清单变成几百条，只见树木，不见森林——没人说得清这些碎片合起来到底是个什么样的产品。

《用户故事地图》的作者 Jeff Patton 说，问题出在：我们把用户故事当成了“要完成的任务”，而不是“用户的一段旅程”。于是，他提出了一个简单却强大的方法——把故事摊开，画成一张地图。

📌 一张用户故事地图的样子（以“在线购物”为例）
浏览商品 加入购物车 结算付款 收货 评价
搜索商品 修改数量 选择地址 查看物流 打分
按分类筛选 删除商品 使用优惠券 确认收货 写评论
← 横轴：用户旅程（从左到右） · 纵轴：优先级（从上到下）→

横着看，它是用户从开始到结束的完整旅程——这叫“主干”或“骨架”。竖着看，每个步骤下面挂着大小不一的用户故事，越往上优先级越高、越先做。

Patton 在书里反复强调一句话：故事地图的重点不是图本身，而是画图过程中的对话。

《用户故事地图》的三个关键提醒

💬

故事是对话，不是文档

用户故事不是用来“写需求”的，而是用来“引发讨论”的。地图的价值在于大家围着它聊出了共识。

🗺️

先看全局，再切版本

整张地图是产品的全貌。横向切一刀，就是一个可以交付的最小可用版本（MVP）。

🧠

避免“清单思维”

一张扁平的待办清单会让人只盯着下一条任务。地图用空间结构强迫团队思考上下文。

“用户故事地图是在一次偶然中诞生的——Jeff Patton 的朋友创业做产品，迟迟发不了版。Patton 拉着朋友坐在地板上，让他描述用户会怎么用这个产品，一边听一边写卡片，按时间顺序排在地上。两个小时后，地板上铺满了一整张故事地图。”

—— 这个故事记录在《用户故事地图》一书里

如果你想试一次，只需要三步

① 讲一遍旅程

让一个人从头到尾讲一遍“用户会怎么用”，其他人先别打断，听完。

② 摆卡片

用便签写下每个步骤和故事，贴在一面大墙或白板上。物理卡片比软件好——因为可以随手挪。

③ 横切版本

沿着纵轴切一刀：上面那一刀是做第一版必须有的，下面那一刀可以以后再说。

🔗
地图回答了“做什么”，但还没回答“做到什么程度算完成”
地图上的卡片是“用户故事”。到了开发团队手里，还需要一个东西来回答：
“这个功能具体要表现出什么行为？怎么验证它做对了？”
这就是 BDD、Gherkin 和 Feature 文件 登场的地方。

02 BDD · Gherkin · Feature 文件

BDD（行为驱动开发）用一套叫 Gherkin 的“半自然语言”，把地图上的用户故事翻译成具体的、可执行的验收场景，写在 Feature 文件 里。这三者连在一起，就形成了一条从“看见全局”到“精准落地”的链条。

📌 回到地图 —— 聚焦“结算付款”下的“使用优惠券”
浏览商品 加入购物车 结算付款 ← 当前聚焦 收货 评价
搜索商品 修改数量 使用优惠券 查看物流 打分
按分类筛选 删除商品 选择收货地址 确认收货 写评论
← 横轴：用户旅程 · 纵轴：优先级（上高下低）→

假设团队决定先做“使用优惠券”这个用户故事。按照经典的用户故事格式，它可能是这样的：

# 用户故事：使用优惠券
作为 一位在线购物的顾客，
我想要 在结算时输入优惠码，
以便 获得折扣，花更少的钱买到商品。

这个描述很清楚，但它还不够——“输入优惠码”到底要处理哪些情况？过期券怎么办？无效券怎么办？一个订单能用几张？ 这些细节，就是 BDD 和 Gherkin 要解决的问题。

三个核心概念，一句话说清

🤝

BDD 是什么

一种协作方法。让业务、开发和测试坐在一起，用具体例子讨论“系统应该表现出什么行为”。由 Dan North 于 2006 年提出。

📝

Gherkin 是什么

BDD 使用的语言格式。用 Given / When / Then 三个关键词，把对话结果写成人和机器都能读的场景。Cucumber、SpecFlow、Behave 等工具都支持它。

📄

Feature 文件是什么

用 Gherkin 写出来的文件，扩展名是 .feature。它既是需求文档，也是自动化测试的输入。

“BDD 首先专注于能够交付业务价值的特性，然后通过具体的实例——也就是场景——来确保团队对需求有一致的理解。”

—— John Ferguson Smart，《BDD In Action》作者

Gherkin 的五种关键词，像讲故事一样写需求

Gherkin 的语法非常精简。你只需要记住五个词，就能把任何一个用户故事展开成完整的行为规范：

# Feature：功能标题（对应一个用户故事或功能组）
Feature: 使用优惠券

# Background：所有场景共用的前置条件（可选）
Background:
  Given 顾客已登录
  And 购物车中已有商品

# Scenario：一个具体的场景（一条路径）
Scenario: 使用有效的优惠券
  Given 顾客有一张有效的优惠券
  When 顾客在结算时输入优惠码
  Then 订单总价应减少相应折扣
  And 页面应显示折扣金额
Given

前置条件

描述场景开始时的系统状态。“世界在故事开始前是什么样子？”
例：顾客已登录、购物车中已有商品

When

动作

描述触发行为的关键操作。一个场景通常只有一个 When——如果有多个动作，应该拆成多个场景。
例：顾客输入优惠码

Then

预期结果

描述可观察到的结果。必须是外部可观测的，而不是内部状态。
例：订单总价减少、页面显示折扣

And / But

延续上一步

用来延续前面的 Given、When 或 Then，让场景读起来更自然。
例：And 页面应显示折扣金额

“用陈述式，不要用命令式——写‘用户登录’，而不是‘用户点击了坐标 (350, 480) 的按钮’。”

—— Cucumber 官方最佳实践指南

完整的 Feature 文件：一个用户故事的“全貌”

把“使用优惠券”这个故事展开，一个完整的 .feature 文件长这样——它覆盖了正常路径和几个关键边界情况：

# coupon.feature

Feature: 使用优惠券
  作为 一位在线购物的顾客
  我想要 在结算时输入优惠码
  以便 获得折扣

Background:
  Given 顾客已登录
  And 购物车中有商品“无线耳机”

Scenario: 使用有效的优惠券
  Given 顾客有一张“满100减10”的优惠券
  When 顾客在结算时输入该优惠码
  Then 订单总价应减少10元
  And 页面应显示“已优惠10元”

Scenario: 优惠券已过期
  Given 顾客有一张已过期的优惠券
  When 顾客在结算时输入该优惠码
  Then 页面应显示“该优惠券已过期”
  And 订单总价不变

Scenario: 优惠码无效
  When 顾客输入一个不存在的优惠码
  Then 页面应显示“无效的优惠码”
↑ 每一个 Scenario 就是一条可独立验证的验收标准

注意这个文件的结构：Feature 的标题和描述直接对应地图上的用户故事；Background 把多个场景共用的前置条件抽出来；三个 Scenario 分别覆盖了正常路径、过期券和无效券——这三个场景合在一起，才完整定义了“使用优惠券”这个故事的验收标准。

进阶：Scenario Outline——当同一场景有很多组数据

如果优惠券有多种面额，与其复制粘贴多个几乎一样的场景，不如用 Scenario Outline + Examples 来一次搞定：

Scenario Outline: 不同面额的优惠券
  Given 顾客有一张面额为 <面额> 的优惠券
  And 订单原价为 <原价> 元
  When 顾客使用该优惠券
  Then 订单总价应变为 <最终价> 元

Examples:
  | 面额  | 原价  | 最终价 |
  | 10元  | 100元 | 90元  |
  | 30元  | 200元 | 170元 |
  | 50元  | 100元 | 50元  |
↑ Examples 表格中的每一行都会生成一个独立的测试用例

这样写的好处是：场景逻辑只写一遍，数据的变化通过表格管理，既清晰又不容易漏掉边界值。

BDD 的完整工作流：从对话到自动化

① 发现

业务、开发、测试坐在一起（“三剑客”会议），围绕地图上的用户故事讨论具体例子。这一步最重要。

② 表述

把讨论结果用 Gherkin 写成 Feature 文件。不是在写文档，而是在记录共识。

③ 自动化

为每个 Gherkin 步骤编写自动化代码（Step Definition），让场景变成可运行的测试。

④ 实现

编写产品代码，让场景通过。先写场景，再写代码——这是 BDD 区别于传统开发的关键。

“BDD 场景在代码写完之前就写好了。只有当一个场景通过，意味着所有人对你说的话都达成了一致，你才能开始实现。”

—— Cucumber 官方反模式指南

实践中的四个大坑（以及怎么避开）

🕳️

把场景写成 UI 脚本

“点击按钮”“输入框填入”——这些是实现细节，不是行为。好的 Gherkin 描述的是业务结果。

🕳️

一个场景塞太多行为

“注册 + 登录 + 改密码 + 下单”——一个场景只测一条路径。超过 5–7 步，大概率需要拆开。

🕳️

写完代码再补场景

如果场景是在代码之后写的，它就不再是“共识的记录”，而变成了“事后解释”。先讨论，再写场景，最后写代码。

🕳️

场景之间互相依赖

“上一个场景创建了订单 #12345，这个场景来查看它”——这会让测试脆弱且难以并行。每个场景自己准备数据。

回到地图：它们是一条线上的珍珠

用户故事地图和 BDD / Gherkin / Feature 文件，不是两件事，而是同一条工作流上的不同环节：

🗺️
故事地图
看见全局
→
🤝

建立共识
→
📝

📄

可执行规范

地图回答“我们要做什么”和“先做什么”——它是全局的、可视的、用于规划和沟通的。

Feature 文件回答“这个功能具体要表现出什么行为”和“怎么验证它做对了”——它是局部的、精确的、可执行的。地图上的每一张故事卡片，都可以展开成一个或多个 Feature 文件（或者一个 Feature 文件中的多个 Scenario）。

“用户故事是一个关于对话的承诺。地图让这场对话有了全局的上下文，而 Gherkin 让这场对话有了精确的记录。”

—— 综合《用户故事地图》与 BDD 实践
