# 概述

把需求整理成大小合适、具有用户价值的故事，放入正确的故事地图步骤和交付切片，并在获得同步授权后安全地更新远端 Storymap。

## 工作流程

1. 确定交付范围。
   - 请求涉及创建、编辑、校验、拉取、推送、转换或打开故事地图时，必须先运行 `storymaps --version`。如果命令不可用或运行失败，直接运行 `npm install -g storymaps`；安装后必须再次运行 `storymaps --version` 验证。安装或验证失败时停止并报告错误，不得继续执行 CLI 操作。
   - 只要求编写、改进或拆解故事而不操作故事地图时，跳过 CLI 检查和安装，直接按工作流程产出候选故事。
   - 用户只要求编写、改进或拆解故事时，输出候选故事，不修改地图，并跳过地图定位、结构编辑和远端同步步骤。
   - 用户要求添加或编辑故事地图时，修改本地源文件；同步远端必须由用户明确要求。用户在当前请求中已明确要求同步时，无需重复确认。
   - 将“生成用户故事地图，基于以下材料：...”视为创建或编辑故事地图的请求，继续执行第 2-6 步；只有用户明确要求同步时才执行第 7 步。若材料需要拆解，先执行第 4 步规定的 9 个拆分模式。
   - 只询问会影响角色、用户价值、拆分结果、目标步骤或交付切片的缺失信息；已有上下文足够时直接继续。

2. 定位源文件并建立基线。
   - 默认使用仓库根目录的 `storymap.yml`。存在多个候选文件且无法从上下文判断时，询问目标路径，不要猜测。
   - 确定源文件后记录其路径；后续所有 CLI 命令都必须显式使用该路径，不得回退到默认的 `storymap.yml`。
   - 读取源文件及其 Git 工作区状态，保留已有的 `name`、`id`、`site` 和未涉及的结构。
   - 创建新地图或无法确定字段结构时，读取 `assets/storymap-template.yml`，再替换占位符；新地图获得远端 ID 前不要写入 `id` 字段；不要复制模板中的占位业务信息。
   - 需要远端版本作为编辑基线时，先确认本地没有未保存修改，或取得用户明确授权后再运行 `storymaps pull --file <源文件路径>`。

3. 编写或改进故事。
   - 创建、改写或添加故事时，读取 `references/story-writing.md`。
   - 故事 `name` 使用简短、面向结果的标题；`body` 只包含一句用户故事：`作为一个[XX角色]，我[想要什么]，[以便达到什么目的]。`
   - 不要把验收标准、Given/When/Then、实现方案、背景说明或拆分理由写入 `body`。

4. 判断是否需要拆解。
   - 用户提供的是史诗，或一个故事包含多个目标、操作、角色、业务规则、数据类型、界面方式，无法可靠估算，或明显无法在一个迭代内完成时，读取 `references/story-refinement.md`。
   - 需要拆解时，必须先执行该文件的“拆解前检查”，再按“拆解顺序”中的 1-9 个拆分模式逐项判断，采用第一个适用模式；拆出的故事仍过大时从模式 1 重新检查，并同时遵守其中的禁止拆法、输出与确认、结果检查要求。
   - 优先形成能独立体现用户价值的纵向切片；不要按前端、后端、数据库或其他技术层拆分。
   - 目标是写入地图，且拆解会把一张卡片变成多张卡片时，先展示候选子故事及其步骤、切片建议，获得用户确认后再写入地图。
   - 新的大故事拆解后只添加子故事，不再添加父故事。拆解已有卡片时，经确认后用子故事替换父故事，避免重复表示和重复计点。

5. 编辑地图结构。
   - 将 `steps` 排成用户完成目标所需的简短、有序步骤。
   - 让 `users[].step` 和 `activities[].step` 精确引用已有步骤；不要创建悬空引用。
   - 将每个 `users[].color` 设置为 `#fca5a5`，将每个 `activities[].color` 设置为 `#93c5fd`；不得使用其他颜色或省略这两个字段。
   - 将交付增量放在 `slices` 中，并把故事放在 `slices[].stories.<step>[]` 对应步骤下。优先沿用已有步骤和切片；没有合适位置时才新增。
   - 卡片只使用 `name`、`body`、`color`、`status`、`points`、`tags`、`url` 字段。`status` 只能是 `done`、`in-progress`、`planned` 或 `blocked`；不适用的可选字段应删除，而不是留下空占位值。
   - 新卡片没有指定状态时使用 `planned`。不要臆造点数；拆分时不要把父故事点数复制给每个子故事。只有确有共同来源时才沿用父故事的标签或 URL。
   - 保持 YAML 缩进、字符串引号和现有语言风格；使用 YAML 结构编辑，不要用字符串拼接修改数据。

6. 校验本地文件。
   - 修改后运行 `storymaps validate <源文件路径>`。
   - 命令返回非零退出码时，读取 stderr，修复行号所指的语法、缩进、键名或字段类型问题，然后重新校验；校验未通过时停止，不得推送。
   - 只有用户要求交换格式时，才使用 `storymaps convert`，并在转换后重新校验目标 YAML。

7. 审阅并同步远端。
   - 需要相关命令、同步顺序或失败处理时，读取 `references/storymaps-cli.md`。
   - 源文件已有 `id` 时，推送前运行 `storymaps status <源文件路径>` 和 `storymaps diff <源文件路径>`；汇总信息不足时运行 `storymaps diff --full <源文件路径>`。
   - 源文件没有 `id` 且请求未提供明确远端目标时，视为新地图且没有远端基线，不运行 `diff`；校验通过且用户明确要求同步时，直接运行 `storymaps push --file <源文件路径>` 创建远端地图，成功后运行 `storymaps status <源文件路径>`。
   - 对已有远端基线的地图，检查步骤顺序、故事归属、状态、点数、标签、URL 和删除项。出现未预期的远端改动、元数据不匹配或无法确认的删除时停止并报告。
   - 对已有 `id` 的地图，仅在用户明确要求同步、校验通过且差异符合预期后运行 `storymaps push --file <源文件路径>`。推送成功后再次运行 `storymaps status <源文件路径>`；推送失败时报告输出，不要声称同步成功。

## 边界情况

- 找不到默认源文件：搜索 `storymap*.yml`；找不到时只在用户要求创建地图的情况下新建。
- 故事引用的步骤不存在：同步更新 `users`、`activities` 和 `slices` 中的引用，再重新校验。
- 故事没有可观察的用户价值：先重新表述或与相关工作组合，不要把纯技术任务伪装成用户故事。
- 不确定性导致无法拆解：提出限时调研建议；调研不是用户故事，不要用用户故事句式写入地图。
- `storymaps pull --file <源文件路径>` 可能覆盖工作副本：未检查本地修改或未获授权时不要执行。
- 差异包含意外远端修改：核对 `id`、`site` 和远端版本，不要直接推送覆盖。

## 验证

1. 检查每个新增或改写故事只有一个主要用户目标，`body` 只包含规定的用户故事句式。
2. 检查子故事没有按技术层拆分，父故事未与子故事重复保留或重复计点。
3. 修改地图后运行 `storymaps validate <源文件路径>`，确认退出码为 0。
4. 已有 `id` 的地图，推送前审阅 `storymaps status <源文件路径>` 和 `storymaps diff <源文件路径>`；无 `id` 的新地图跳过 `diff`；推送后再次运行 `storymaps status <源文件路径>` 确认最终状态。
