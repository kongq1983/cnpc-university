# Write Skills

## 概述

写 SKILL.md 的核心心法一句话：**description 决定技能何时被触发，body 决定触发之后跑得怎么样**。body 的每一行都在和对话历史争夺模型注意力——只写模型默认不知道的信息。

## 工作流程

1. **澄清意图。** 询问（或从对话中提取）：
   - 这个技能要让 agent 具备什么能力？
   - 哪些用户措辞 / 场景应该触发它？哪些不应该触发？
   - 期望的输出格式是什么？
   - 输出能否被客观验证（→ 需要评估）？还是主观的（→ 跳过评估）？

2. **判断自由度分级**：
   - **低自由度**（脆弱操作，每次执行必须完全一致：数据库迁移、生产部署）→ 给出参数极少的脚本。
   - **中自由度**（有推荐模式但允许微调：API 调用封装）→ 伪代码或带参数的脚本。
   - **高自由度**（多条路径都成立：代码 review、文案创作）→ 描述目标和判断标准，让 agent 自选路径。
   用这个分级来校准后续指令的强制强度。

3. **起草 frontmatter。**
   - `name`：小写 + 连字符（如 `write-skills`），与目录名保持一致。
   - `description`：至少两句话——先说做什么，再写明确的正向触发条件（"当用户……时使用"）和负向触发条件（"不要用于……"）。宁可写得"激进"一点：agent 漏触发的概率远高于误触发。
   - **语言选择**：description 用与目标用户相同的语言写，可混入英文关键词覆盖中英夹杂的问法。若需同时在中英文对话中触发，写中英双语两份。改写对照范例见 `references/description-patterns.md`。

4. **起草 body。** 复制 `assets/skill-template.md` 作为骨架，并遵循以下写作规范：
   - **语态**：全程祈使句、第三人称命令（写"提取文本"，不写"你应该提取"）。
   - **强度标记**：不能跳过的步骤用「必须」，少用"始终 / 永不"——「必须」的合规率更高。
   - **输出格式**：把字面模板放进 `assets/`，用指针引用（"必须严格遵循 assets/template.json 中的结构"），不要用散文描述结构。
   - **代码示例**：目标是 ~50 token 的可复制代码 + 期望输出。跳过原理解释。
   - **错误处理**：列出真实的错误信息 → 对应的修复动作。"酌情处理错误"等于没写。
   - **术语**：每个概念全程只用一个词（URL / 路径 / endpoint 混用会干扰模式匹配）。
   - **嵌套**：`SKILL.md → references/foo.md` 只挂一层，绝不 `foo.md → bar.md`，防止 agent 预览前 100 行时静默丢失内容。
   - **围栏卫生**：body 内尽量不放代码块围栏，确需展示模板骨架时把模板移入 `assets/`。
   对 body 的每一行执行**无操作测试**：如果删掉这句话 agent 的行为不会变，就删掉整句。模型本来就知道 PDF 是什么、HTTP 是什么，不要解释概念。

5. **抽取资源文件。** 凡是符合下列条件的内容，一律移出 body：
   - 确定性、可重复的逻辑 → `scripts/`
   - 只在特定条件下才需要读的参考资料 → `references/`
   - 固定的输出模板、schema、图标 → `assets/`
   body 里只留：何时调用每个资源（每个指针一行）。

6. **用 agent 读者验证。** 开一个全新对话，把 SKILL.md 贴进去，问："如果你刚触发这个技能，逐步执行时哪一步会让你卡住或需要猜测？" 每一处犹豫 = 一个幻觉源头 = 把那行改写得更具体。

7. **跑评估**（仅当输出可客观验证时）。构造 2–3 个真实测试提示，在同一轮对话里分别跑"带技能"和"不带技能"两个版本，评分、迭代。schema 与字段约定见 `references/evals.md`。

## 示例

**示例 1：触发措辞**
输入："一个帮助做仪表盘的技能。"
输出 description："为公司数据展示构建快速内部仪表盘。当用户提到仪表盘、数据可视化、内部指标，或想以任何形式展示公司数据时使用——即使没有明确说出'仪表盘'三个字。不要用于面向公众的营销网站。"

**示例 2：无操作测试实战**
输入："PDF 是一种常用于分享文件的文档格式。"
输出：（删除——无操作测试判定为 no-op；模型本来就知道这一点）

**示例 3：自由度分级**
输入："为一个数据库迁移步骤写指令。"
输出："必须先运行 `python scripts/migrate.py --env production --dry-run`。如果 exit code ≠ 0，停止并上报 stderr。禁止直接执行正式迁移。"（低自由度 → 脚本 + 硬闸门）

## 边界情况 / 坑

- **body 里的"何时使用"是死重。** body 是触发之后才加载的——它无法影响触发。所有触发条件必须放进 `description`。
- **概念解释是负价值。** 耗 token 且不改变任何行为。
- **过度精简会砍掉功能。** "帮我精简"的请求经常删掉的是功能而不是废话——重新跑一遍无操作测试，而不是对通过测试的句子修剪字词。
- **脚本是给 agent 用的工具，不是给用户用的库。** 错误信息必须打印人类可读、可自解释的内容；exit code 必须有意义；脚本里不塞业务逻辑。
- **对单个样例过拟合。** 如果技能只能处理构建它时的那个具体任务，就要有意识地抽象：去掉仓库专属名词，为整类任务而写。
- **body 超过 500 行。** 停止编写——拆分到 `references/`，并给每个指针加上明确的"何时读取"条件。

## 验证

1. 把自己当成刚触发技能的 agent，走一遍 body。标记任何需要猜测的步骤。
2. 检查每个 reference 指针都有明确的"何时读取"条件。
3. 检查 description 同时包含正向触发（"当用户……时使用"）和负向触发（"不要用于……"）。
4. 逐句跑无操作测试：删除 → 问行为是否变化 → 恢复或舍弃。
5. 用 markdown 预览器渲染一次 SKILL.md，确认围栏没有嵌套断裂、frontmatter 完整。
6. 如果有评估：确认带技能的通过率高于基线，且没有任何断言在两个运行里都通过（无法区分两次运行的断言没有价值）。
